# Architecture (condensed)

The full, authoritative tour is in [`CLAUDE.md`](../CLAUDE.md). This is the short version.

## Message → response

`src/index.ts` wires it together:

1. **`channels/imessage.ts`** polls `~/Library/Messages/chat.db` every 2s, pulls any
   image/PDF/audio attachments, and hands the message to a registered handler. It also
   passively logs *every* observed message to `imessage_log` (both directions).
2. **`user-resolver.ts`** maps the sender handle → a `User` (name, tone, allowed groups),
   built from `config/profile.json`.
3. **`group-resolver.ts`** maps the chat → a `GroupConfig` (its tools + context path). DMs
   map to the admin context, but only after step 2: a sender who isn't in the profile is
   dropped silently in `index.ts`, and a profile user without `admin` in `allowedGroups`
   gets a redirect, not the admin tools.
4. **`router.ts`** classifies the message `sync` vs `async` (a low-cost model call with a
   regex fallback). Async work runs in the background.
5. **`agent.ts`** runs the tool-use loop (written to the OpenAI Responses shape; `lib/openai.ts`
   hands every call to Claude instead when `LLM_PROVIDER=claude`) with a per-group scoped tool set and a
   system prompt assembled by **`context-resolver.ts`**.

## The system prompt

`context-resolver.ts#loadSystemBlocks` builds the prompt in two cache-friendly segments:

- **staticPrefix** (stable per group + tone): identity, voice, the always-on owner
  profile, the group's `CLAUDE.md`, security rules, and the callable tool list + routing.
- **dynamic** (per message/minute): a precomputed date lookup table, recent memory, and
  retrieval blocks (Learned Preferences / Relevant Knowledge / People Context) keyed off
  the incoming message.

The adapter sends them as one instruction string with the stable segment first, preserving
a cacheable prefix for provider-side prompt caching.

## Persistence (`src/db.ts`, one SQLite file)

- **facts + facts_fts** — atomic knowledge with FTS5 retrieval; preferences/decisions/
  metrics supersede, commitments/feedback append.
- **people + emails + phones + interactions** — the CRM/relationship layer.
- **tasks** — synced to Google Tasks; organic reminders with escalating backoff.
- **memory** — operational key/value state (counters, dated briefs, checkpoints).
- **messages / imessage_log / async_tasks / work_requests / actions / *_extraction_log** — history,
  passive capture, background work, cross-repo request IDs/status, the spend-gated actions queue,
  and daemon cursors.

## Background loops

- **scheduler.ts** — daily/weekly cron (morning brief, inbox triage, evening wrap-up,
  weekly briefs) + the 22:00 nightly reflection.
- **heartbeat.ts** — 30-min proactive check-ins (critical overdue, "time to leave",
  conflicts), honoring quiet hours.
- **brain-pulse.ts / idea-pulse.ts** — twice-daily proactive scans that surface aging
  commitments / pitch grounded ideas.
- **Daemons** (launchd KeepAlive, not cron): `meeting-daemon`, `imessage-daemon`,
  `inbox-signal-daemon` — extract structured signal from meetings, texts, and email.

## Configuration

`src/config.ts` loads `config/profile.json` (generated by onboarding) — the single source
of truth for the assistant's identity and the people it serves. Nothing personal is
hardcoded; with no profile present, generic defaults keep everything booting.

## Gotchas worth knowing

- ESM imports use `.js` extensions even in `.ts` source (NodeNext). Don't "fix" them.
- `tsc` (`npm run build`) is the only typechecker; there's no test runner.
- `chat.db` is read-only — outbound messages go through AppleScript.
- Personal/generated files are gitignored; see `docs/CUSTOMIZING.md`.
