# CLAUDE.md

Guidance for Claude Code working in this folder.

## If the user says "set me up"

Follow [setup/GUIDE.md](setup/GUIDE.md) step by step. The person is probably not technical. Start by running `npm run doctor -- --setup --json` to see what's already done, then continue from the first step that isn't `ok`. Plain language, one step per turn, check each step before moving on, never ask for secrets in the chat.

The same applies to "turn on <feature>", "add phone calls", "set up the family chat", etc.: find the matching step in the guide.

## If the user says "update me"

Follow "Updating" at the end of [setup/GUIDE.md](setup/GUIDE.md): pull the latest code, keep their personal files (they're gitignored), rebuild, restart the background service, re-run the checker, and tell them in plain words what changed (`CHANGELOG.md`). Never throw away their changes or force anything without asking. A folder downloaded as a ZIP can't pull; the guide shows how to turn it into one that can.

## What this is

A personal assistant people text over iMessage. It runs on their own Mac: it polls `~/Library/Messages/chat.db`, runs a tool-use agent on Claude or OpenAI (`LLM_PROVIDER`), and replies via AppleScript. Memory lives in a local SQLite file. See [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Commands

```bash
npm run build                    # typecheck + compile to dist/
npm run dev                      # run in the foreground (tsx, no build)
npm run onboard                  # the setup interview → config/profile.json, context/, .env
npm run doctor -- --setup        # is this Mac ready? (--json for machine-readable)
npm run doctor                   # is it running healthily?
npm run install:service          # install/refresh the background service (launchd)
npm run restart | pause | resume
npm run auth:google              # connect Google (calendar, tasks, Gmail)
npm run test:<name>              # isolated tests; see package.json
```

There's no test runner; each `scripts/test-*.ts` is a standalone script with its own temporary database.

## Where things are

- `src/index.ts`: boot + the inbound message handler.
- `src/modules.ts`: every feature as a module; `config/profile.json` `modules` switches them on/off.
- `src/lib/openai.ts`: the one place model calls go. Cost: `instructions` is only the stable prompt prefix (cacheable, `prompt_cache_key` per group); the per-message context goes in as a developer message before the owner's message. History is the last `HISTORY_LIMIT` (40) messages; tool results are capped at `TOOL_OUTPUT_MAX_CHARS` (head + tail), and a context overflow shrinks earlier tool results and retries once (`shrinkToolOutputs`). Follow-up watch checks run on the router model. `createOpenAIResponse` switches to `src/lib/anthropic.ts` when Claude is the provider, translating the request/response shape both ways (Claude's thinking blocks are replayed verbatim across tool turns). Phone calls (`src/phone.ts`) always use OpenAI's realtime voice API.
- `src/agent.ts`: the agent loop. `src/context-resolver.ts`: builds the system prompt.
- `src/tools/`: agent tools, registered in `src/tools/index.ts`.
- `src/cos-outbound.ts` + `src/checkins.ts`: all proactive messages go through here (short check-ins, a small daily interrupt budget). New proactive code must not call `sendMessage` directly.
- `src/tools/actions.ts`: the approval gate for anything that spends money or speaks for the owner; `send_now` / `call_now` / `book_online` / `do_online` skip it only when the owner's own words asked for it. Proposals reach the owner as the plan in plain words + "Go?" (`src/lib/proposal-text.ts`); action ids stay with the model.
- `src/phone.ts`, `src/errands.ts`, `src/wakeup.ts`, `src/web-booking.ts`, `src/web-task.ts`: things it does in the world.
- Wake-up calls (`src/wakeup.ts`) gather the morning first (`src/morning.ts#morningBriefing`: today's Google events deduped with `clashes`, overdue/due-today owner tasks, `openItems` waiting on the owner; each source time-boxed, cached per morning so retries reuse it) into `WakeCallInfo.context`. With context the call wakes the owner, walks the day, acts through `ask_assistant`, and ends with a one-line plan; without it, the old questions. `WAKEUP_MAX_CALL_MIN` 15. Tests: `npm run test:wakeup`.
- Website jobs (`src/web-task.ts`, tool `do_online`): cancel, export, change a setting in the owner's Chrome. Each browser run is time-boxed; the job keeps going run after run (progress carried into the next prompt, resumed after a restart) until done, blocked on the owner (`needsOwner`: login, payment, decision, phone-only), or out of runs. Website work never goes through `computer_use`; its `start_task` refuses website plans while Chrome is connected. The Chrome extension offers `snapshot` (numbered clickable elements), click by index or visible text, `scroll`, and an in-page pay-button guard. There is deliberately no run-page-JavaScript action.
- The job tracker (`src/jobs.ts`, tools `whats_going_on` / `stop_job` / `answer_job`): one plain-words list of everything in progress across website jobs, errands, follow-ups and email threads. Jobs wait for the owner (a login, a texted code, a decision) instead of failing; texted codes are typed by `enter_owner_code` and never reach the model (single-use, 10 minutes, same site only). Check-ins list open jobs, waiting-on-you first.
- Follow-ups (`src/followups.ts`, tools `watch_for` / `email_errand`): watches that check email until something happens (after a cancellation: the confirmation email, and no new charge where the site showed a billing date), and email threads with companies that answer simple questions, follow up once after 3 business days, then offer a call.
- `src/lib/preferences.ts`: the owner's saved "how I like things done" go into every job's prompt. `src/lib/photo-caption.ts`: a one-line caption is kept with any photo the owner sends.
- Sign-ins inside website jobs: `src/lib/code-finder.ts` fetches a fresh code or emailed sign-in link from the owner's email (through the configured email source) or a code text their iPhone forwards, and finds which address a company emails them at. The job types codes with `enter_owner_code` and opens links with `open_sign_in_link`; neither reaches the model, both are single-use, 10 minutes, same site or its billing provider. Pop-ups a page opens become the job's tab. Optional 1Password sign-ins (`src/lib/onepassword.ts`, tools `fill_login` / `fill_2fa_code`): with a read-only service account (`OP_SERVICE_ACCOUNT_TOKEN`) limited to one vault (`OP_VAULT`), a job fills the saved login whose URL matches the page's site, straight into the page (a password only into a `type=password` field, extension 1.6.0); the model only sees "filled" or a refusal. Jobs try it before asking the owner, never click forgot/reset links, and text at most one question per 15 minutes. A `practice` job never texts, waits on the owner, or opens follow-up watches.
- Browser control (extension 1.7.0): the assistant's tabs live in their own unfocused Chrome window (`botWindowId`), screenshots come from DevTools `Page.captureScreenshot` (visible-tab capture only for a tab already showing), and tab switches happen only in that window; Chrome relaunches with `open -g`, `showJobTab` brings Chrome forward only after 2 minutes idle (`takeover.ts#idleSeconds`), and the job's `desktop` tool refuses input while the owner is using the Mac. Snapshot reads every frame and open shadow root; screenshot + click_at for screens the page map can't explain; real_click / real_type / real_key send trusted input through Chrome's DevTools protocol (Chrome shows a "being controlled" bar). `set_files` attaches uploads without opening the file picker (only files the owner listed in `do_online` `files`, from Downloads/Desktop/Documents, never secrets). For Chrome/macOS windows the page can't reach (a file dialog, a permission prompt), website jobs get a scoped `desktop` tool, live only while a job's browser run is open. Pay buttons and card fields are guarded on every path. No run-page-JavaScript action, on purpose.
- Omi (optional module `omi`, `OMI_MCP_KEY`): the `omi` connector in `mcp-servers.json` keeps only its get/search tools, callable only in the owner's own runs (`ownerOnlyReadTools` in `src/tools/index.ts`). `src/omi-sync.ts` reads each new Omi conversation every 15 minutes and saves the owner's promises, dated to-dos, people and decisions, all owner-private (sensitive). Omi's own to-dos are ignored. Conversations Omi tags `entertainment` are skipped. Household members' own talk (a partner on their work call, which Omi may label as the owner) is saved as facts about them, not as the owner's tasks/contacts; useful media (tutorials, reviews, talks) is kept as non-sensitive `reference` notes. A conversation is read only once it has been finished `OMI_SETTLE_MIN` (45) minutes; transcripts go to the model as compact `You: … / Speaker N: …` lines (`src/lib/omi-transcript.ts`); fragments under 25 words are skipped unless they sound like a to-do; the same audio recorded twice (phone + desktop) is read once (5-word-shingle fingerprint, the copy that tags one voice as the owner wins); the prompt lists recent open tasks so reworded repeats aren't added; a spoken first name reuses the one recent contact with that name (`personIdFor`). An empty transcript or an Omi error is retried for up to 48h; long meetings are read in up to 5 parts (`transcriptParts`) and merged; Omi's own summary and to-dos go in as hints; to-dos a colleague assigns, promises to deliver and agreed calendar changes count; a repeat recording needs overlapping times (`sameRecording`); a conversation that grew is re-read only for its new part (`read_ends`); recordings under 80 words are read as a voice note; profile `people` may carry `fullName` and `aliases`. `npm run omi:reread -- <id>...` re-reads as a dry run (`--save` / `--apply-from`). Tests: `npm run test:omi`.
- Speaking coach (`src/speech-coach.ts`, `omi` module, tool `review_my_speaking`, owner only): each real two-way conversation the Omi sync reads gets counted numbers (talk share, turns, longest stretch, questions, fillers, hedges, words a minute) in `speech_reviews`; work conversations of `OMI_DEBRIEF_MIN` (15)+ minutes get one coaching call staged for the next check-in (max `SPEECH_DEBRIEFS_PER_DAY`); `SPEECH_COACH_CRON` (Sunday 6:50) stages a weekly summary by setting vs the week before. Tests: `npm run test:speech-coach`.
- Desktop tasks (`computer_use` `start_task`): while a task window is open a message gets `DESKTOP_TASK_MAX_TURNS` (40) steps and keeps only the last 8 tool results whole; one go covers the task (within `COMPUTER_USE_TASK_RESUME_MS`, 30 min, `start_task` on the owner's own message re-opens the window; `end_task` ends it). Every interactive message's last step says what's done and not done, never "I'm on it". Done-guard (`src/task-done-guard.ts`): after a reply to the owner's admin message that says something is finished and no task tool ran, the router model matches it to open tasks and closes them. Tests: `npm run test:desktop-task`.
- Calls with the owner: `call_me` on the owner's own message rings at any hour (`PHONE_CALL_ME_DAILY_CAP`); the assistant's own rings keep quiet hours and `PHONE_RING_DAILY_CAP`. Every owner dial uses answering-machine detection (voicemail → hang up + a text). The assistant speaks `PHONE_OWNER_SPEAK_MS` after pickup and hangs up with a text after `PHONE_OWNER_DEAD_AIR_MS` of silence. Owner calls see the last 3 hours of texts (`recentTextsForCall`) and transcribe in `PHONE_TRANSCRIBE_LANGUAGE` (retried without it if refused). Refused webhooks log why. Tests: `npm run test:call-me`.
- Ongoing topics (`src/threads.ts`, table `threads`, owner + Family chats): before a reply, `pickThreads` matches the message and the last few turns to the open topic it continues (no cue words needed) and `threadBlock` adds that topic's record to the prompt; after the reply, `updateThreads` folds the exchange in, starts a topic only for a real multi-turn subject, and closes finished ones. Quiet 60 days → closed. `THREADS_ENABLED=false` turns it off. Tests: `npm run test:threads`.
- Job progress (`src/lib/job-updates.ts#updateOwner`): short `reply` updates on errands and website jobs the owner started. Milestones always go; in-between progress waits 45 minutes, at most 8 a day, never the same text twice; raw API errors are stripped. Errand results go to the owner directly, each call says what it ran into and the real next call time (`nextCallLine`, never "calling now" when it's tomorrow), and a quiet errand gets one "still on it" line after 3 hours. A website job whose AI service fails (out of credit, outage) pauses with one plain text and retries every `WEB_TASK_INFRA_WAIT_MS` without using up a try. Tests: `npm run test:job-updates`.
- Call notes (`call_notes` table, `errands.ts#recordCallNote`): every errand call and callback that reached someone records who they spoke with, what was said, any reference number, direct line, and promise, plus a sensitive `call note` fact on the business. Earlier notes go into the next call's brief and callbacks, and the owner's result text says "(Spoke with Pat, front desk; ref 4471.)".
- `search_messages`: a person's name matches every phone and email on file for them (`handlesForName`); `since`/`until` take local calendar days (a bounded window reads in conversation order); lines show local times and names.

A call with the owner is saved into their admin thread when it ends (wake-up calls excluded).
- `src/lib/chrome-health.ts`: pings the extension each minute, reopens Chrome, reloads an outdated extension, alerts once a day if a website job is paused on it.
- `src/family-*.ts`: the shared family chat. It has strict privacy boundaries; `npm run test:family-access` must keep passing. Photos sent there become a separate `photo` source that can ground an event's or item's details but never authorizes a change; mistyped adds ("Did milk to the list") and "add it to the list" (item from a member's earlier message) count; repeating events take a `repeat` rule grounded in their words. Calls, bookings and website jobs go through `ask_owner` (`src/family-requests.ts`): the owner's own requests run at once in their DM thread; anyone else's go to the owner, whose `family_request` approve lets the member's exact words pass `ownerAsked` for 30 minutes; a 1-minute tick posts the result back. Tests: `npm run test:family-smarter`.
- Research (`src/research.ts`, tool `research` on the `web` and `family-web` keys): open-ended asks (things to do, trips, food, shopping, services). Builds a profile of who's asking (owner chats: non-sensitive facts about the owner, family members and kids, home, saved preferences, live location if fresh; Family chat: Family memory only), plans 3-5 searches, runs them in parallel with hosted web search (`OPENAI_RESEARCH_MODEL`), fills gaps in a second round, then writes 5-8 options with why each fits plus a best plan. Tests: `npm run test:research`.
- Reception (`src/reception.ts`, tool `call_screening` on the `errands` key; `RECEPTION_ENABLED`, default on): calls to the assistant's number from anyone but the owner or a business calling back are answered as a receptionist. `connectDecision`: contacts get put through by day, everyone in `through` mode, nobody in `messages` mode, only always-ring people during `RECEPTION_QUIET` (default 19-8 local); a forged caller ID never rings. `connect_owner` redirects the caller's Twilio leg to the owner's cell with a whisper ("Name, about X. Press 1 to take it."); anything else sends the caller back to take a message. Messages are texted as `reply` (quiet hours: held for the check-in, except a known contact's urgent one on the `reception-urgent` lane). An automated call reading a verification code is let finish (silence-based turn detection on reception calls) and `codeFromCall` texts the owner the code at once; reception transcripts are kept a day in `memory` group `phone`. Texts to the number (`/twilio/voice?step=sms`, Twilio-signature checked) are forwarded to the owner (`smsForwardText`), codes on the `reception-urgent` lane. If OpenAI drops a call at accept, the line is hung up and a wake-up call rings again in 30s. Tests: `npm run test:reception`.
- Errand calls: targets carry opening `hours` (`parseHours`, looked up with web_search); the runner only dials while they're open (`isOpenAt`, skipping the first 5 and last 20 minutes). Conference mode (`PHONE_CONFERENCE`, default on) puts the business and the assistant's SIP leg in one Twilio conference, so `press_keys` is a conference announcement and the session never drops. The business's side is transcribed (`PHONE_TRANSCRIBE_THEM`) so a dropped call says why. A dial the business answered but our voice never joined means the phone link is down: it isn't counted, all dialing pauses an hour, and `checkPhoneLink` (`tailscale status`, `TAILSCALE_BIN`) texts once when the tunnel's been off 10 minutes and once when it's back. Every call result is texted. At most `ERRAND_PER_BUSINESS_DAILY_CAP` (2) real dials a day to one number across errands (`countCallsToNumberToday`, from `dialing` events); their "stop calling" (`askedNotToCall`) puts the number in memory `do-not-call`, which `prepareErrand` refuses and the runner skips; a `menu_stuck` review moves on to the next target, a voicemail or closed recording waits ~20h. A bare "go" confirms the pending proposal listed in the prompt instead of re-proposing.
- Take-over (`src/lib/takeover.ts`, `src/takeover-server.ts`): when a website job needs the owner's hands (a login, a captcha), the ask carries a one-time link (30 min) to a page that shows this Mac's screen through noVNC relayed to Screen Sharing on 127.0.0.1:5900 (`TAKEOVER_BASE_URL`, tailnet-only via `tailscale serve`); Done resumes the job, "Couldn't do it" stops it. `TAKEOVER_URL` (vnc://) is the fallback. `change_job` changes a running job (errands: a note; website jobs: merged into the next run as "OWNER CHANGED THE PLAN"). Unanswered asks get up to 2 reminders, 4h apart (`jobCheckIns`). Tests: `npm run test:takeover`.
- Job journal + checker: every job step (start, update, ask, answer with codes/links never written, run result, check, done/failed/stopped) goes to `job_journal`; `whats_going_on` with `which` reads one job back step by step, and the dashboard lists every job this week with its journal. `src/lib/verify.ts#checkDone` (router model, `DONE_CHECK_MODEL`) reads goal + claim + evidence before anything is reported done: errand calls (being sent to a website or another number is `blocked`, not done), website jobs (the final page; not verified → keep going), online bookings, follow-up watches and email threads (which now quote their `evidence`). It fails open if the checker errors; isolated tests skip it unless `setDoneChecker` stubs one. "Want me to call them?" answered yes starts `call_now` instead of re-checking email.
- One task per thing: `src/lib/task-dedupe.ts#similarOpenTask` (shared specific word + most words) stops `create_task` and Omi sync from adding a to-do that is already open. `call_now` reuses an open errand to the same place by number or by name (front desk vs reservations line), and errand calls are told never to invent a detail (confirmation numbers, names, dates) they weren't given. Buying words (buy, order, top up, credits, upgrade) count as the owner asking for a website job; the payment guard is unchanged.
- Errand calls connect the assistant first (`PHONE_ASSISTANT_FIRST`, default on): its SIP leg joins a silent conference, then the business is dialed in via the Participants API (`?step=biz` starts the timers when they pick up), so there's no dead air. Without it, the business hears `PHONE_HOLD_LINE` while the voice connects and the assistant speaks after 1.2s. `PHONE_RECORD_CALLS=true` records two channels plus the whole conference for diagnosing drops. Errand calls have no barge-in (`semantic_vad` eagerness low, `interrupt_response: false`) so line noise can't cut the assistant off mid-word; `PHONE_BARGE_IN=true` restores it. Business calls (not reception, barge-in off) also run an echo guard (`PHONE_ECHO_GUARD`, default on): `create_response: false`, and a heard turn that started while the assistant was talking (or within 1.5s of its estimated last word) is dropped with `conversation.item.delete` when `isEcho` says it's 2+ words mostly the assistant's own; no transcript in 2.5s → answered as before. Owner calls don't barge in either (`PHONE_OWNER_BARGE_IN=true` restores it), use `PHONE_OWNER_NOISE_REDUCTION` (far_field; dropped on a 4xx retry), keep each turn to a sentence or two, and log how often sound came in over the assistant and how much of it had no words. The business leg's `StatusCallbackEvent` is sent as one parameter per event (a single space-joined string is ignored, so pickup never fired). Opener and turn-taking (call review step 3): `openerRule(bot, full, recorded)` is one sentence ending on the question ("Hi, this is <assistant>, <owner>'s AI assistant[, on a recorded line]. <question>?"); once a Bot line passes `isIntro`, `session.update` swaps in `afterIntroRule()` (never introduce again); `lib/reply-gate.ts` waits `PHONE_YIELD_MS` (700) after their turn and holds the reply if they start again; business calls get `PHONE_NOISE_REDUCTION` (near_field) and `PHONE_TURN_EAGERNESS` (low); voicemail gives `callbackNumber()`; their goodbye ends the call. Call review (step 1): `lib/call-timing.ts#CallTimeline` keeps a timed transcript and reply delays, `phone.ts#reviewAndLog` gets the end reason (our hangups or the business leg's `completed` → `they_hung_up`), `call-log.ts#reviewCall` (`CALL_REVIEW_MODEL`, 25s, skipped in isolated tests) writes answered_by/verdict/learned/next_step, `applyReview` turns a dropped call where a person gave something into `blocked`; rows in `call_log` (transcripts cleared after `CALL_LOG_KEEP_DAYS`). Practice line (step 2): `src/practice-line.ts`, six TwiML scenes on `/twilio/voice?step=practice` (signature-checked, only while `armScene` is set and the call comes from `TWILIO_NUMBER`), `gradeScene` from `call_log`, `npm run practice`, one a day via the canary with `PRACTICE_LINE_ENABLED`. Silent errands (`jobs.ts#isSilentErrand`) stay out of `openItems`/`list_errands`. Texts the assistant sends the owner are saved in the admin thread (`cos-outbound` `deps.remember`); `errands.ts#isBusinessContact` lets a saved business through the personal-contact check. `PHONE_FORWARD_NUMBERS`: extra Twilio numbers that just forward (calls ring the owner's cell with the real caller ID, texts forwarded). Long website runs keep only the last few tool results whole (`keepRecentToolOutputs`) and write a DONE/LEFT handoff on their last step (`finalTurnNote`); `BROWSER_MAX_TURNS` 60. Every tool call is counted in `tool_use`.
- Call stages (`src/lib/call-stage.ts`, `src/menu-nav.ts`, `PHONE_CALL_STAGES`): on assistant-first business calls the code keeps greeting / person / menu / hold / voicemail / recording from each transcribed turn (`classifyLine`) and Twilio's answering-machine verdict (`PHONE_BUSINESS_AMD`, `?step=amd`). `respond()` waits up to 2.5s for the last turn's transcript before acting. Menus: no speech; `MenuNav` asks `MENU_NAV_MODEL` for press/say/wait/stuck, no repeat within 3s, a looping menu climbs 0 → "representative" → stuck. Hold: silent until a person-like turn. Voicemail: after the beep (or `PHONE_VOICEMAIL_CUE_MS` of quiet) `leaveVoicemail` uses `voicemailRule()`; "to send your message, press 1" is pressed (`sendMessageKey`). Intros said to a machine don't count. Until a person is on (and with people too unless `PHONE_PERSON_LISTEN=semantic`) listening uses server VAD (`PHONE_FAST_SILENCE_MS` 500). Their goodbye makes the next turn a short goodbye + `end_call` (`isGoodbye`). `call_log.stages` holds the path. `applyReview`: a person confirmed it and hung up → done; hung up on the intro → failed, next place. A reply-mode voicemail with places left moves on. Silent errands have their own cap (`PRACTICE_DAILY_CALL_CAP`, `countErrandCallsToday({ silent })`). Tests: `npm run test:call-states`.
- Safety net (`src/call-safety-net.ts`, `PHONE_SAFETY_NET`): staged errand calls get `check_with_owner` (texts the owner on the `owner-call` lane and awaits `openAsk`, `PHONE_ASK_WAIT_MS` 150s; the owner's next admin text is the answer via `takeAskAnswer` in `index.ts`) and `bring_in_owner` (adds the owner's cell to the conference, 18s ring, `?step=owner`; on pickup the assistant's leg gets `EndConferenceOnExit=false`, it hands over and ends `done` with `handedToOwner`, which skips the checker). While waiting it only says "Still checking…" every 20s. `takeOverCall` / `answerCallAsk` / `setCallsChanged` are hooks for a companion app. Tests: `npm run test:safety-net`.
- Stall watch (`src/lib/stall-watch.ts`, core start key `stall-watch`): every freeze over `STALL_LOG_MS` (750) is logged with the tagged log lines before it, last 30 in memory `system/stalls` (`npm run stalls`). The watchdog runs the doctor in a child process (`dist/doctor-json.js`; in-process under tsx) and skips its tick while a call is live.
- Text loops (optional module `text-loops`, off by default; only useful when Messages on the Mac is the owner's own Apple ID): `src/text-loops.ts` reads the owner's changed text threads in `imessage_log` every `TEXT_LOOPS_INTERVAL_MIN` (10). It never reads privacy-scoped rows (family), `GROUP_*` chats, 1:1 chats with known users, short codes, tapbacks or codes. Each open loop is a job of kind `text_loop` (`owe_reply`/`i_promised` wait on the owner; `waiting_on_them`/`plan` are watched); the owner's later message closes what they owed, untouched items stop after 7 days, at most 15 open; `answer_job` marks done, `stop_job` dismisses. Nothing is sent. `npm run texts:loops -- [days]` is a dry run. Tests: `npm run test:text-loops`.
- Watchdog (`src/watchdog.ts`, core module, `WATCHDOG_ENABLED`): every 10 minutes the doctor's checks plus disk, the public phone link and the AI service; something broken 30 minutes → one `reply` text with the fix (once a day each), then one when it's fixed. Weekly scorecard (`src/scorecard.ts`, check-ins module, `npm run scorecard [-- --review]`): jobs finished, calls that worked, checker catches, questions asked, the task list and cost, with week-over-week change and the top 3 failure causes + fixes, staged into Sunday's morning check-in and saved under `SCORECARD_DIR`. Morning check (`src/canary.ts`, phone module, opt-in `CANARY_ENABLED=true`, `npm run canary`): a silent practice call to a recorded time line (errand envelope `silent`: no texts, no call notes) and one read-only signed-in check from `CANARY_SITES`; texts only on failure.
- Site rules (`src/lib/site-rules.ts`, tool `site_permissions`, `web-booking` key, owner only): per-site levels in `memory` group `site-rules`, keyed by `siteKey` (examplebank.com / secure.examplebank.com / "ExampleBank" → `examplebank`). `read` = look only: `do_online` refuses a task with change words (`siteRuleRefusal`) and the job prompt says LOOK ONLY. `ask` (no rule) = the default. Tests: `npm run test:site-rules`.
- `get_ride` (`src/tools/rides.ts`, `web-booking` key): Uber or Lyft in Chrome via `do_online`; pickup defaults to the owner's `home_address` fact; it always pauses with the price for a yes and never touches payment.
- Standing family OKs (`family-requests.ts` grants, tool `family_permission`): person + kinds + about + until (≤3 months) + max_usd. A matching `ask_owner` request runs at once and the owner gets a heads-up; it never covers paying.
- `instacart_cart` (`src/tools/instacart-cart.ts`, `web-booking` key): fills the owner's Instacart cart in Chrome from items and/or the Family Groceries list, stopping before checkout. A thin wrapper over `do_online`.
- `context/`: prompt files. Personal ones are generated by onboarding and gitignored; `context/_examples/` holds templates.

## Rules

- Imports use `.js` extensions even for `.ts` files (NodeNext ESM).
- Never write to `chat.db`.
- Keep personal data out of the repo: `config/profile.json`, `.env`, `context/<group>/`, `context/shared/{identity,voice,profile}.md` and the database are gitignored. Examples use made-up names.
- Times: use `getTimezone()` / `src/lib/time.ts`, never a hardcoded zone.
